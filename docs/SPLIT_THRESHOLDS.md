# msg / dfs 拆分决策阈值

`im-core` 现在是单体部署,`msg`(消息读写)和 `dfs`(文件上传凭证)只是内部按包分的模块,跟
`session`/`biz`/`sync`/`status`/`idgen` 共享同一个 JVM、同一套数据库连接池。这篇文档记录:
为什么这两个包(而不是别的包)是未来拆分的候选、拆分的信号是什么、以及拆的时候具体怎么拆——
不是提前拆,是提前想清楚"什么时候该拆、拆了要干什么"。

## 为什么候选是 msg 和 dfs,不是别的包

`im-core` 内部七个包里,`session`/`biz`/`sync`/`status`/`idgen` 的资源画像和访问模式高度相似
(轻量 CRUD + Redis/MySQL 单行读写),没有谁明显拖累谁,拆开收益不大。`msg` 和 `dfs` 不一样,
各自有独立到不需要跟其它包一起扩缩容的理由:

- **`msg` 是全平台唯一的高 QPS、延迟敏感路径**:每一条聊天消息都经过 `MessageWriteService`(幂等
  去重 → 敏感词 → 回调 → 落库 → 同步通知 → 推送发布),压测验证过单实例 5 万连接、P99 投递延迟
  29ms(详见 [`docs/LOAD_TEST_REPORT.md`](LOAD_TEST_REPORT.md))。这是唯一一个"业务量涨了就必须
  单独扩容"的包,其它包的调用量基本跟在线用户数线性相关,不会像消息量那样有独立的、可能脉冲式增长
  的曲线。
- **`dfs` 的资源画像和峰值时间点都跟 `msg`不相关**:`FileUploadService` 只是签发/确认 MinIO
  预签名 URL,I/O 瓶颈在 MinIO 自己那边,不在 im-core;文件上传是突发的(比如群里有人发了个视频,
  短时间内一批用户集中下载),这个峰值跟消息发送峰值(比如某个热点事件导致消息量暴涨)没有必然
  关联。两个不相关的峰值放在同一个实例里,意味着容量规划要按"两个峰值的和"来算,比分开各自按
  自己的峰值算更浪费。

## 拆分信号(达到才考虑拆,不是提前拆)

按优先级从"最值得信任"到"最早期预警"排列:

1. **单实例扩容打到 `msg` 的容量天花板,但 `session`/`biz`/`dfs` 还有大量富余**:压测里验证过的
   单实例基线是 5 万连接 / P99 29ms;如果生产消息 QPS 已经逼近这个量级,而此时给整个 `im-core`
   加实例(横向扩容)意味着连带把 `session`/`biz`/`dfs` 也多复制了一份、但它们的负载远没到需要
   扩容的地步——这时候"只扩 msg 一个包"比"扩整个 im-core"划算,是最直接的拆分信号。
2. **数据库连接池出现跨域竞争,拖累不相关的接口**:`application.yml` 里 HikariCP 池子已经从默认
   10 调到 50(注释里写明原因是 `Authenticate` 突发并发查询),这本身就是"一个域的流量压力影响
   到共享资源池"的先例。如果观察到消息发送高峰期间,`GetUserInfo`/群组操作这类跟消息无关的接口
   P99 也跟着一起劣化,说明 `msg` 已经在通过共享连接池拖累其它域,是需要拆分的信号,而不是继续
   调大池子能根治的问题(调大池子只是推迟这个信号出现的时间)。
3. **`dfs` 出现独立于消息流量的资源脉冲**:比如一次营销活动导致大量用户短时间内批量上传媒体文件,
   如果这类脉冲开始影响同一 JVM 里消息收发的响应时间(GC 停顿、线程池排队),说明 `dfs` 的峰值已经
   大到需要隔离,不能再依赖"文件上传本来就轻量"这个假设。
4. **发布节奏耦合带来运维摩擦**:如果 `msg` 相关的高频迭代(新消息类型、推送策略调整)导致
   `session`/`biz`/`sync` 这些跟消息无关的域被迫跟着频繁重新部署,或者反过来——`biz` 的变更让
   `msg` 团队被迫等发布窗口——这是组织/流程信号,不是性能信号,但同样是该拆的理由。

**没有以上任何一条成立之前不建议拆**:现在只有一次本地压测的验证数据,没有真实生产流量;拆分会
新增两套独立的部署单元、健康检查、扩缩容策略和 on-call 复杂度,在没有证据表明单体撑不住之前,
这些成本纯粹是浪费。

## 真要拆的话,具体怎么拆

这是这个项目现有架构决定的、比较关键的一点:**内部服务边界已经按 gRPC service 划好了**,拆分不是
重新设计,是"把已经存在的边界提升成物理部署边界":

- `MessageServiceGrpc`(`msg.proto`)的唯一实现类 `MessageGrpcService` 只依赖
  `MessageWriteService`/`MessageQueryService`/`AckService`/`ConversationSettingService`,
  以及 `conversation` 包的 `RecipientResolver`(消息扩散投递要知道群成员/单聊对端是谁)。把
  `msg` + `conversation` 两个包整体搬到一个新的 `im-msg` 模块、独立打包部署,`im-gateway` 那边
  只需要把 `CoreGrpcClients.message` 这个 gRPC stub 指向新的 host:port,**协议不用变,
  `MethodRegistry` 里的路由代码完全不用动**——这正是当初把 gateway 到 im-core 之间的调用统一
  收敛成 gRPC(而不是直接方法调用)的意义所在。`sync` 包(`t_update_log` 增量同步)要留在哪边
  取决于消息发送后写同步日志这一步算不算 `msg` 的强依赖——目前是同步调用(见
  `MessageWriteService.send` 里的 `syncNotifier.onMessageSent`),拆的时候要么把 `sync` 一起
  搬过去,要么把这一步改成消息队列异步化解耦,是拆分时需要做的架构决策,不是搬包就完事。
- `FileServiceGrpc`(`file.proto`)的唯一实现类 `FileGrpcService` 只依赖
  `FileUploadService`/`MinioStorageClient`,对 `t_file` 表的访问完全独立,不依赖 `msg`/`biz`/
  `session` 任何一个包。`dfs` 包的拆分是纯粹的"整体搬走",风险最低,是三个候选里最容易先动手的
  一个。
- 两边拆分都低风险的前提,是现有代码已经在包与包之间强制走 gRPC service 类作为唯一入口(没有
  `msg` 包直接 new 一个 `biz` 包内部类这种跨包直接引用),这个约束在"合并 session/bff/biz/msg/
  sync/status/idgen/dfs 到 im-core"那次重构里就已经定下来了,拆分时是在吃这个设计决策的红利,
  不需要重新划边界。

## 结论

当前不拆。`docs/LOAD_TEST_REPORT.md` 里的单实例基线(5 万连接、P99 29ms)是判断"是否接近 msg
容量天花板"的参照系;真实生产流量出现、上面任意一条信号成立时,再按这篇文档里写的路径拆
`im-msg`/`im-dfs` 出来。
